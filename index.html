Section 4 · Part 3 of 3

Make your first project folder

  1. Make a folder called my-first-page inside a folder named dev in your user folder. Avoid Desktop and Documents, because OneDrive syncs them and slows projects down.
  2. Open it in VS Code: File → Open Folder, pick my-first-page, and choose “Yes, I trust the authors”.
  3. Make a file: in the Explorer press the New File icon and name it index.html. The name matters later, because websites look for a file called index.html first.
  4. Fill it quickly: type ! then press Tab. VS Code writes the standard page skeleton for you. Or paste the page from the live editor.
  5. Save with Ctrl + S. Then find the file in File Explorer and double-click it. It opens in your browser. That is your page, still only on your laptop.
Optional: install the Live Server extension. Right-click index.html and choose “Open with Live Server” to see changes the moment you save.

Section 5 · Part 4 of 5

Create a GitHub account and send your page up

  1. Sign up at github.com. Pick a username you would show an employer. Verify your email with the code GitHub sends.
  2. Turn on two-factor sign-in: profile photo → Settings → Password and authentication. Use an authenticator app and save the recovery codes.
  3. Create a repository (a project folder on GitHub): the + at the top right → New repository. Name it my-first-page, choose Public, and leave the README option off.
  4. Send your files up from Git Bash. Replace YOUR-USERNAME. The first push opens a browser window: press Authorize.
  5. Refresh the repository page. Your files are online, with the commit note beside them.

Publish with GitHub Pages

  1. Open your repository on GitHub and go to Settings → Pages.
  2. Under Build and deployment, set Source to “Deploy from a branch”. Choose branch main and folder / (root), then press Save.
  3. Wait a minute or two and refresh. A green box shows your link: https://YOUR-USERNAME.github.io/my-first-page/.
  4. Open it on your phone. Send it to a friend. You are on the internet.

If something goes wrong

The link shows “404 – page not found”

The file must be named index.html and sit at the top level of the repository, not inside a folder. File names are case-sensitive online, so Index.html is a different name.

It worked before, but my change is not showing

Check the commit and push both happened (git status). Then wait a minute, and hard-refresh the page with Ctrl + F5.

The push is rejected or asks for a password

GitHub no longer accepts your account password for Git. Use the browser sign-in window, or set up an SSH key. If the repository already had a README, run git pull origin main --rebase first.

“git is not recognized” or “code is not recognized”

Close every terminal and open a new one. Programs only learn about new installs when they start.

Git inside: snapshots and sticky notes

A commit is a snapshot

It stores your project as it looked at that moment, with your note, the time, and a pointer to the commit before it. Each has a short code, such as a3f9.

A branch is a sticky note

A label stuck on one commit. Make a new commit and the note moves forward with you.

Where it lives

In a hidden folder called .git inside your project. Delete it and the history goes.

Press Make a commit a few times, then Create a branch and commit again. Switch between branches to see which note moves.

Branches are like trying a design change on a copy of the drawing, while the approved drawing stays untouched until you merge.

React in deployment: from your source to files a browser can open

Browsers cannot read JSX. A build tool (Vite) compiles and bundles the source into plain HTML, CSS and JavaScript, and only that output is deployed.

Under the hood · Part 9 of 20

How the browser runs a React app

A single-page application (SPA): the server sends one shell page, and React builds and updates the interface in the browser.

Why refreshing can show 404

On a static host, refreshing /plans asks for a file named plans, which does not exist. The fix is a rewrite rule that sends every address to index.html, and then React Router shows the right page. Vercel and Netlify have a setting for this.

Public by design

Everything in a React app is downloaded by every visitor, so never put a secret in it. Vite only exposes variables starting with VITE_, and even those are visible.

React with Vite vs Next.js

Vite: the browser builds the screen after loading. Next.js: the server can build the HTML first, so the visitor sees content sooner. Next.js is a better fit when search engines must read your pages.

Vercel inside: build once, serve from everywhere

The build step

Some projects need a preparation step that turns your source into final files. Vercel notices the type of project and runs it. A plain HTML page needs none.

A CDN

A content delivery network: many servers around the world holding the same files.

Many shops stocking the same product, so each customer collects from the nearest one.

Preview and production

A push to your main branch updates the real link. Pushes to other branches get their own preview link to test first.

Backend code

It runs in short on-demand functions, started when a request arrives and stopped after. It is not a server that stays on.

You set it up by importing a GitHub repository. Button names change, so look for “Add New → Project”.

Under the hood · Part 13 of 20

Render inside: a computer that stays on for your program

Two commands you provide

A build command (get ready, for example install packages) and a start command (run the program). Render runs the first once and keeps the second running.

Health check

Render keeps asking a page you choose, such as /api/health, “are you alive?” If it stops answering, Render restarts the program.

The free-plan catch

A free service sleeps after 15 minutes without visitors, so the first visit afterwards takes about a minute. Its free databases expire after 30 days, which is why GlucoPlate keeps its database on Neon.

Auto-deploy

Every push to the chosen branch triggers a fresh build and restart by itself.

Under the hood · Part 14 of 20

A whole app deployed: React, backend and database together

What each host holds

Vercel: the React files. Render: the running backend. Neon: the database. Three services, three links, three jobs.

Who knows which secret

The React app holds only public values, such as the backend’s address. The backend holds the database address and the signing key, set in Render’s dashboard.

Why CORS exists

Cross-Origin Resource Sharing: the server lists which websites may read its replies.

A browser stops one website reading another’s data unless the second site says “that one is allowed”.
Under the hood · Part 15 of 20

Secrets: how a host gets your passwords safely

Secrets are configuration values, such as database addresses and API keys, that must never be committed to a repository.

If a secret reaches a public repository, treat it as stolen: change it at its source straight away. Deleting the file later does not erase the history.

Under the hood · Part 17 of 20

DNS in depth: who answers when you type a name

The Domain Name System is a distributed, hierarchical directory that maps names to IP addresses, with caching at every level.

Three levels of directory

Root servers know who runs each ending (.com, .app, .ke). Ending servers know who runs each name. The name’s own servers hold the real answer.

Caching and TTL

Time to live: how long an answer may be remembered.

Everyone keeps a copy of the answer for a while so nobody asks the whole chain each time.
